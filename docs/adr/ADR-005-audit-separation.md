## 背景

v1.0 方案声称审计日志"WORM 不可篡改"，却又把审计与业务数据放在同一 TimescaleDB 实例。业务库的备份恢复、DBA 操作、超管 UPDATE 都能改审计记录——WORM 承诺无法兑现；且审计写入高峰与业务查询争抢资源。

## 决策

**审计与业务数据物理分离，审计采用 append-only 存储 + 哈希链防篡改。**

- **SaaS**：独立审计 PostgreSQL 实例，应用账号仅 `INSERT/SELECT`（无 UPDATE/DELETE）；每条记录附前一条哈希构成哈希链，每日落一条锚点哈希到对象存储 WORM 桶；业务库只保留审计索引（ID + 摘要）供关联查询；
- **单机私有化版**：本地 append-only JSONL 文件 + 哈希链，随一键备份归档；
- 审计写入**异步化**（本地 WAL 缓冲 + 批量提交），避免高峰期拖慢业务链路，接受秒级窗口（异常崩溃时缓冲未落盘部分会丢，已明示接受）。

审计覆盖：数据访问、LLM 请求/响应、工具调用、CLI 指令、API 调用——Agent 全生命周期行为留痕，保留 180 天。

## 理由

1. **合规承诺必须可验证**：同库存储的 WORM 是自相矛盾的，客户安全团队一问就破功——这是选择独立存储而非"加个审计表"的根本原因；
2. **哈希链 + 外部锚点**：即便拿到库权限，修改历史记录也会破坏链，且外部锚点提供独立证据；
3. **诚实处理单机版**：客户拥有 root 时哈希链只能检测不能防止，交付文档明示"篡改检测 + 客户自担"，**不使用与 SaaS 相同的措辞**——这是刻意的一致性要求。

## 后果

- 正面：合规卖点可验证；审计写入与业务查询资源解耦；
- 负面：多一个存储组件与备份策略对象；异步写入有秒级丢失窗口；
- 撤销条件：引入具备原生 WORM 能力的对象存储作为主审计存储（届时哈希链仍保留用于连续性校验）。
