# ADR-011: 影子降噪转正模式（shadow / enforce）

- **状态**：已接受
- **日期**：2026-09-11
- **关联**：M1 出口验收（W6-3 评估 100% 达标）、R6-6（Gate 计数持久化）、F-11（通知抑制执行）

## 背景

影子期纪律（ADR-001 / W4-1.4）：降噪判决只标注不拦截，告警全量放行。M1 出口标准 1（准确率 >85%）已由 W6-3 评估达成（100%，34/34 段，租户 eval-20260911e），降噪从"记录"进入"执行"的条件满足（D13=C 路线）。

## 决策

1. **模式开关**：新增环境变量 `OPS_NOISE_MODE`：
   - `shadow`（默认）——行为与 M1 完全一致：判决落库、不拦截、不通知；
   - `enforce`——`WouldSuppress=true` 的判决交给通知闸门（notify.Gate）真拦截；`false` 的放行并全渠道通知；
   - 非法值**启动失败**（与 `OPS_NOISE_WINDOW` 同纪律：静默回退会让运维以为配置生效了）。
2. **判决照常落库**：enforce 模式下影子判决（alert_event）继续全量记录——这是转正首周与影子基线做"双跑对比"的数据基础，也是评估链路（evaluate.py）不需要任何修改就能持续验证的原因。
3. **一键回退**：`OPS_NOISE_MODE=shadow` + 重启即回影子。不需要数据迁移、不需要代码变更；拦截动作本身不产生持久副作用（通知是外发消息，簇/判决数据两种模式同构）。
4. **灰度策略**：M1 为单租户形态，模式是全局开关；按租户灰度留到多租户落地（M3 候选）。转正流程定为：先在评估/联调环境 enforce 观察 ≥1 天 → 生产 shadow 双跑对比 1 周 → 生产 enforce。
5. **计数持久化**（R6-6 收口）：Gate 的 suppressed/dispatched 累计值经 `GateStatsSink` 写入 `notify_gate_stats`（migrations/000011，单行/租户覆盖写），启动期恢复——重启不清零。权威明细仍在 alert_event（每告警一条 verdict），本表是 Gate 视角的快速计数，两者可对账。

## 理由与取舍

- **env 开关而非运行时 API**：转正是"改变系统承诺"级别的动作，重启级别的仪式感是刻意设计——防止误触；同时避免在闸门路径上引入运行时可变状态。
- **不拦截"告警本身"，只拦截"通知"**：采集、落库、建单链路不受 enforce 影响——降噪的对象是通知噪声，不是数据完整性。审计与事后分析永远看全量。
- **同步 Admit**：渠道 Send 自带 ≤5s 超时（Notifier 契约），闸门在引擎锁外同步执行，与落库 IO 同一锁边界纪律；不异步化——丢"放行失败"的可观察性比省几毫秒更贵。

## 后果

- 正面：降噪开始产生真实价值（通知量下降）；回退成本 ≈ 0；计数可对账。
- 代价：enforce 误拦截的风险由"评估环境 ≠ 生产分布"引入——缓解：默认 shadow、双跑对比 1 周、闸门决策可由 alert_event 完整回放。
- 未决：通知渠道的真实实现（webhook/IM）与值班升级规则属 W9-2/W9-3；本 ADR 只锁定模式语义与闸门接线。

## 补充（W9-2，2026-09-11）：通知判定口径

落地通知渠道时收敛了 `Gate` 的放行判定——**只有 `new-incident` 放行通知**，`dedup-window`（窗口重复）与 `cluster-merge`（故障域并入既有簇）都不重复通知。理由：转正要交付的价值就是"一个故障域一个通知"，并入告警对新信息量贡献为零却会制造噪声。

- 计数口径：`Stats.Suppressed` = 未发通知总数（两类之和）；细分原因查 `alert_event.payload.reason`（每告警一条判决，可对账）。
- 无指纹/未参与判定的告警（`Reason` 为空）按 new-incident 处理——宁可多通知，不可漏。
- 渠道配置：`notify_channel` 表（迁移 000012），`console` 兜底渠道恒在且为保留名（enforce 零渠道 = 通知静默丢失，兜底至少留痕）；配置经 REST/控制台 CRUD 后**热重载**注册表（不重启生效）。
- 投递仍为同步（Notifier 契约自带 ≤5s 超时），失败计入 `gateFailures`；异步队列+重试留 W9-3（值班升级规则同批）。

## 补充（W9-3，2026-09-11）：严重级路由与值班升级

**严重级路由**：渠道可声明 `min_severity`（`critical` > `warning` > `info`，`notify_channel.min_severity`，迁移 000013），`Registry.Dispatch` 按告警严重级逐渠道判定投递——"critical 进 IM、info 只留日志"由此表达，不需要为每个渠道写独立规则表。

- 未知/空严重级按 `critical`（最高）处理：路由的失败模式必须是**多通知**而非静默丢弃；
- 路由跳过不计入 `Dispatch` 错误；但全部渠道都被过滤掉时返回 `ErrNoChannel`（确定性报错，而非"假装发出去了"）；
- `console` 兜底渠道 `MinSeverity` 恒为 `info`（什么都能收）——它是最后一道留痕。

**值班升级（最小版）**：`OPS_ESCALATION=on` 启用后台扫描（`EscalationPoller`）：`state=open` 且创建超过 `OPS_ESCALATION_AFTER`（默认 15m）的事件，再发一次 `[超时未响应]` 通知。

- **只发一次**由台账 `incident_escalation`（迁移 000014）的 `(tenant_id, incident_id)` 主键保证：`INSERT ... ON CONFLICT DO NOTHING` 只有真正插入成功者认领，多实例安全；发送失败 `Release` 回滚认领，下一轮重试（失败补偿 → 至少一次 + 幂等）；
- **不经 Gate**：升级是"对既有事件再提醒"，与降噪判定（该不该第一次通知）正交——Gate 管首次，Poller 管"发了没人理"；
- 只对 `open` 升级：`acked` 即人工接手（R2 语义），不再催；
- 严重级沿用事件自身 → 走上面的渠道路由；
- 边界：不做排班/轮岗/多级升级（M3）；无 DB 时台账退化为内存（重启即丢、单实例），启动打 WARNING。
