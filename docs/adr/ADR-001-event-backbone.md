## 背景

告警 → 降噪 → RCA 是产品核心闭环，需要一个事件骨干。候选：Kafka、NATS JetStream、Redis Streams。

目标量级：中小租户，单租户 <1k 事件/分钟；团队规模小，无力维护 Kafka 集群。

## 决策

**采用 Redis Streams 作为事件骨干，并明确其定位为"加速层"而非"真相源"。**

配套三项强制约束（v1.1 C2）：
1. 告警流与缓存拆为**独立 Redis 实例**（见 ADR-004）；
2. 消费者组 + pending 消息超时自动 `XCLAIM` 接管（心跳 30s，超时 120s）；
3. 告警簇状态幂等落库 TimescaleDB（以指纹 + 簇 ID 为主键 upsert），Redis 数据丢失后可从库重建。

升级预案：单租户事件 >5k/min 或客户要求更强可靠性时，切换 NATS JetStream——Stream 抽象层已隔离实现，迁移只改适配层。

## 理由

1. **量级匹配**：中小租户量级远低于 Kafka 的经济适用区间，引入 Kafka 是过度设计且抬高可用运维面；
2. **组件数最少**：单机私有化版要能在客户低配机器上跑，每多一个组件就多一处故障点与交付成本；
3. **"加速层非真相源"是真正的保险**：Redis 的持久化语义确实弱于 Kafka，但只要真相在库里，Redis 丢失只是重放延迟而非数据事故。这个原则比选哪个中间件更重要。

## 后果

- 正面：组件少、私有化交付轻、成本可控；
- 负面：Redis 不可用期间告警链路暂停（由 ADR-004 的双实例隔离与 pending 接管缓解）；
- 撤销条件：单租户持续 >5k 事件/分钟，或出现因 Redis 语义导致的告警丢失事故。

## 交叉检查提醒

本决策依赖"告警簇状态落库"这一配套设计；**若未来有人优化掉幂等落库，本 ADR 即失效**，必须重新评审。
