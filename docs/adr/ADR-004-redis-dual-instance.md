## 背景

早期方案用单个 Redis 同时承担缓存、队列、轻量存储三职。问题：缓存 LRU 逐出会挤占告警流内存、in-flight 告警随缓存策略被清理、会话状态可能蒸发。

## 决策

**Redis 拆为两个物理隔离的实例，角色固定不可互换：**

| 实例 | 用途 | 策略 |
|---|---|---|
| **alert（告警实例）** | 告警流 Streams、**会话状态**、llm 调度队列（P1-6） | AOF everysec、`noeviction`、不可逐出 |
| **cache（缓存实例）** | 查询结果缓存、拓扑展示缓存等**可重建**数据 | LRU 可逐出 |

强制约束：
1. `config.Validate()` 启动期校验：角色不得互换、两实例地址不得相同（相同即拒绝启动）；
2. `sessionstore.New()` 构造期校验 role，传 `cache` 直接 panic（宁可启动失败，不运行期丢会话）；
3. 两项约束均有单元测试覆盖（`internal/config`、`internal/sessionstore`）。

## 理由

1. **职责隔离消除资源争抢**：缓存压力再大也不会影响告警链路；
2. **把架构约束变成代码级守护**：文档约束会漂移，panic 不会——这是 P1-1 落地的核心手法；
3. **成本近乎零**：多一个 Redis 实例，对中小规模部署无实质负担。

## 后果

- 正面：告警链路可靠性提升，会话不再随机蒸发；
- 负面：单机版容器数 +1（已在 v1.2 部署形态中计入）；
- 撤销条件：改用具备命名空间级隔离与配额的托管服务（届时需在配置层保留角色语义）。

## 交叉检查提醒

新增任何"往 Redis 写东西"的模块时，必须先回答"放哪个实例、丢了会怎样"——**可重建的放 cache，不可重建的放 alert**。
