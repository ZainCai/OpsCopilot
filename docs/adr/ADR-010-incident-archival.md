## 背景

`alert_event`（告警原始流）已有 7 天压缩 + 30 天保留；但 `incident`（工单）与 `incident_audit`（审计）无限增长。工单 resolved 后价值递减，审计是"这单为什么被关/谁合的"的追溯依据——两者生命周期不同，不能一刀切删除。

## 决策

**工单 resolved 满 N 天（默认 90d）后归档；审计长留（仅随单移入归档）。**

1. 归档 = 事务内把「事件本体 + 关联簇 + 审计轨迹」打包成一行 JSONB 写入 `incident_archive`（保留原 id 可追溯），再删原行（`incident_cluster` 由 FK 级联清除）。
2. 归档表用**单表 JSONB 快照**而非按列镜像：schema 稳定（incident 加列不需同步改归档表）、自描述（还原无需跨表拼接）。
3. 执行器为应用层周期任务（默认 6h 一轮；选行 → FOR UPDATE 锁定复核 → 写归档 → 删审计 → 删事件），不用 TimescaleDB add_job——跨三表并生成聚合 JSON，应用层可单测、不依赖扩展版本行为。
4. 配置 `OPS_INCIDENT_RETENTION`（`90d`/`2160h`/`off`）；非法值启动失败；归档表缺失时任务 ERROR 一次并自停。

## 后果

- 好处：热表不随历史无限增长；归档一行即完整上下文；数据不丢（非删除）。
- 代价：**归档数据无 API 暴露**——找回历史需查 `incident_archive` 表；控制台看不到已归档单（可接受：resolved 满期本就不在看板关注范围内）。
- 交叉检查提醒：ADR-005 审计分离口径 —— 审计的 append-only 性质在**热表**内保持；随单入档是"整体迁移"而非"部分删除"，归档行内审计仍然完整。M9（ADR-008）的代际单各自独立归档，代间无外键关系。

## 替代方案（否决理由）

- 直接删除（不留档）：丢失追溯依据，与审计的存在意义矛盾。
- TimescaleDB add_job：自定义过程跨三表 + JSON 聚合，扩展版本行为耦合，调试成本高。
