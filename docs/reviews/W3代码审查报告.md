## 二、发现的问题

### P1（建议尽快修）

**P1-1 `CoverageReport()` 存在数据竞争（topology_sink.go:113）**
`return s.Graph().Stats()` —— `Graph()` 持锁取图指针，但 `Stats()` 遍历 `g.Nodes`/`g.Edges` 发生在**锁外**，与并发 `IngestDiscover` 的写入构成 race。这是修 `IngestDiscover` 漏锁时漏掉的孪生问题："持锁返回引用"不等于"读受保护"。当前 main.go 尚无并发调用方（图暂时只被单线程喂入），但作为公开 API 已具备触发条件。
*建议*：给 Sink 加锁内统计路径（锁内做浅拷贝或直接在锁内调 Stats），并补一条并发测试。

**P1-2 CI 没有跑 `-race`（ci.yml）**
race detector 只在 linux job 加一行 `go test -race ./...` 即可（Windows 本地因 cgo 限制跑不了，这次的漏锁就是这么漏掉的）。并发代码量现在不小（Sink/Store/Webhook 三处锁），没有 race 门禁等于裸奔。

### P2（记录并排期）

- **P2-1 `AsOf` 零值语义不一致**：`AsOf(零值)` 跳过 ValidTo 判定（会把已失效节点返回），而 `ParseAsOf("")` 返回零值、契约上零值=当前。今天无实际影响（Builder 从不设非零 ValidTo），持久层接入后即成真 bug。修法：零值 t 内部转 `time.Now()`。
- **P2-2 Azure nextLink 盲目跟随且带 Bearer**：被入侵/配置错乱的源可把令牌引到任意主机。修法：跟随前校验 nextLink host 与 BaseURL 一致。
- **P2-3 Azure ARM 429 无处理**：ARM 生产高频限流，当前直接失败。修法：按 `Retry-After` 有限次退避重试。
- **P2-4 ChangeStore 无界内存**：进程内 map 永不清理，长跑进程缓慢泄漏。修法：保留窗口（如 7 天）定期清扫，或等持久层。
- **P2-5 nodeCheck 在 ChangeStore 写锁内调用**：未来若钩子回调 Store 自身即死锁。M1 钩子只有 `HasNode`（另一把锁），安全，但需在 NodeCheck 注释里写明"禁止回调 ChangeStore"。

### P3（顺手清）

- webhook 不拒绝尾部多余 JSON（decoder 只取第一个值，`{"a":1}{"b":2}` 静默收一半）。
- `azure.normalize`：id 与 vmId 均空时 Key 退化为 `"azure://vm/id:"`（应直接报错丢弃）。
- ARM 非 200 错误不含响应体摘要，排障缺上下文（摘要时注意别带出凭证头）。
- `TopologySink.Graph()` 仍返回共享指针——已有"不可变约定"注释，但既然有了 `HasNode`，可考虑收窄为包内私有。

## 三、质量评价

- **正确性**：核心语义（置信度不对称默认、幂等、闭区间窗口、半开 [from,to) 可见性、锁纪律）均有测试锁定；并发正确性本轮发现 2 处漏网（P1-1 与已修的 IngestDiscover），共同根因是缺 race 门禁。
- **可读性**：设计决策均落在注释与 ADR，含"为什么"而非仅"是什么"；已知局限不掩盖。
- **测试**：新增约 45 个测试（topology 27 / azure 11 / cmd ~20），覆盖假服务端、分页死循环、闭环语义、拷贝隔离、并发；真实环境走 integration 标签门控，设计得当。
