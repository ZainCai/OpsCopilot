## 三、核心调用链路

1. **采集链**：`Host.Run`(30s tick) → 连接器 HealthCheck/Collect/Discover → `TopologySink.IngestCollect/IngestDiscover`
2. **降噪链（W4 新增）**：`IngestCollect` → `NoiseEngine.ProcessAlerts`（锁内：批级拓扑快照 → Alert→Event → Shadow.Process → Verdict）→ 锁外：脏簇幂等落 Redis
3. **聚类语义**：指纹命中优先 → 故障域命中（CausalSubgraph BFS，同节点距离 0）→ 均未命中新建簇（key = 首指纹@窗口桶号）
4. **变更链**：POST /api/v1/changes（Token 鉴权）→ 严格节点校验（Sink.HasNode 锁内查图）→ ChangeStore.Record（幂等）
5. **重建链**：启动 → Redis HGETALL → `Clusterer.Restore`（key 原样保留，幂等链不断）；DB 真相源 upsert 留 W5 pgx

## 四、架构设计评价（维持优势）

- **模块纪律可执行**：`check_module_boundaries.py` 本轮复跑通过；noise 以 `FaultDomainFunc` 函数注入保持零 internal 依赖，是纪律的正面范例。
- **ADR-001"加速层非真相源"落地完整**：内存簇可丢、Redis 镜像幂等 upsert、Restore 重建演练（miniredis）通过。
- **影子模式纪律**：引擎无拦截路径，判决只记录——W6 评估的数据基础干净。
- **失败取向一致**："宁漏勿杀"贯穿空指纹放行（noise）、部分成功先投递（Host G3）、落库失败不中断告警链路。

## 六、遗留风险与建议（不阻塞，按优先级）

1. **`-race` 门禁本机不可用**（无 gcc/cgo），并发正确性目前依赖 CI race job——确认 GitHub Actions 的 race 步骤覆盖 noise 包（新增高频并发路径）。
2. **resolved 簇内存无限累积**（F2 后不再影响 CPU，但内存仍随 7 天影子期增长）：建议 W5 落库策略接管时给内存历史区加保留上限（如仅保留最近 N 条或 24h）。
3. **DB 真相源缺位**：ADR-001 的"清 Redis 从表重建"目前只验证到 Redis 镜像侧；W5 引入 pgx 后需把 `RecordSink` 双实现并列（Redis + DB），并补 testcontainers 集成测试。
4. **域函数 BFS 逐对判定**（每对 cluster-node × alert-node 一次 BFS）：百台规模无碍；千节点拓扑建议改为预计算连通分量（union-find，O(V+E) 一次）。
5. **Prometheus 连接器无增量水位**（Since/Scope 返回 ErrUnsupported 属设计内）：影子期数据量可控；W6 评估前如需拉长窗口再评估。
