## 一、高危（3 项，均有真实触发路径）

### H1｜listen_guard 可被 `:8080` 形式地址绕过 —— 安全门禁形同虚设
- **问题**：`checkListenSecurity` 把 `host == ""` 当作回环放行（`cmd/opscopilot/listen_guard.go:26`）。但 Go 的 `http.Server` 对 `OPS_LISTEN_ADDR=":8080"` 会监听**全部网络接口**（IPv4+IPv6 通配）——门禁被绕过，写端点无鉴权暴露在所有网卡上，且无任何告警。这正是 D1 决策要堵的场景。
- **根因**：把"host 为空"误等同于"只监听本机"；实际是 TCP 通配地址（与 `0.0.0.0`、`[::]` 同类）。
- **修法**：`host == ""` 按非回环处理（拒绝或要求 token），与 `0.0.0.0` 同口径。一行改动 + 测试用例。
- **已确认**：复核源码属实。

### H2｜M9 代际 ID 与含 `#` 的 sourceRef 碰撞 —— 跨告警串单
- **问题**：第 N 代的 incident_id = `base + "#" + N`（`internal/incident/incident.go:525-530`）。若告警 ref="a" 复发，gen2 的 id 是 `webhook:a#2`，与告警 ref="a#2" 的 **gen1 完全相同**。MemStore 的逐代精确链会把 ref="a" 的告警刷新进 ref="a#2" 的单；PG 侧撞唯一索引后按"另一 worker 抢先"重读 winner（`pg_store.go:537-553`），返回的也是**别人的单**——后续恢复语甚至会把别家的单自动 resolve。sourceRef 来自外部告警 label，内容不可控，`#` 完全可能出现。
- **根因**：M9 设计时我只防了"前缀通配串代"，漏了"精确链碰撞"——后缀方案隐含"base 不含 `#`"这一未声明前提。
- **修法**：两个 `UpsertExternal` 入口一致校验 `strings.Contains(sourceRef, "#")` → 400/错误（存量数据无 `#` 前提可查证；若有则需迁移）。一行校验 + 测试。
- **已确认**：复核源码属实。

### H3｜verdicts 工具租户缺省缺失 —— M1 出口门禁可静默失效（假 PASS）
- **问题**：`tools/verdicts/main.go:37` 的 `-tenant` 帮助文本承诺"缺省读 OPS_TENANT，再缺省 default"，实际未设时把**空串**传入 `tenant_id=$2` → 查出 0 行 → evaluate.py 里所有非静默段 SKIP、所有静默段"无判决 = PASS" → **准确率 100% 的假 PASS**，M1 出口门禁被静默击穿。
- **根因**：昨晚改租户可配置化时，帮文本写了兜底、代码没写。
- **修法**：`if *tenant == "" { *tenant = "default" }`（与 `noise.go` 的 DefaultTenant 口径对齐），并在 verdicts 输出 0 行时向 stderr 告警。
- **已确认**：复核源码属实。

## 六、不确定的部分（如实说明）

1. **processBatch 超时语义（M4）**：两个方案各有代价——对齐超时（简单，但单条慢会拖累整批的时效）vs 按条短事务（粒度好，但失去"行锁覆盖处理全程"的多 worker 保护，需回退到 per-item 锁）。**需要先确认实际部署是单 worker 还是多 worker**：单 worker 下整批事务是安全的，只需把超时对齐；多 worker 才必须做 per-item。这是部署形态问题，不是纯技术问题。
2. **tie-break 排序规则（L9）**：Go 字节序 vs PG 数据库 collation——各自内部自洽（翻页不丢不重），但同一游标跨实现语义可能漂移。是否需要 `COLLATE "C"` 取决于生产库的 collation 配置，需查实际部署参数。
3. **cursor HMAC（L16）**：当前读路径无鉴权、无用户体系，伪造游标只能"翻到任意页"，无提权；是否值得加签名取决于读路径何时加鉴权（D2 的反代方案下可能永远不需要）。
4. **存量 sourceRef 是否含 `#`（H2 修复前提）**：修复方案是"拒绝含 `#` 的新写入"，但**存量数据**若已有含 `#` 的 sourceRef，拒绝策略会挡住它们的合法刷新——需要先查一次库（`SELECT count(*) FROM incident WHERE source_ref LIKE '%#%'`）确认存量情况，这决定修复是"直接拒绝"还是"拒绝 + 存量迁移"。
5. **go-redis v9.6.1 之后的 CVE**：凭知识无法确认 2025 年披露项，需跑一次 `govulncheck` 才能定论。
6. **FK 引用 incident 的表是否只有 incident_cluster（M-待确认）**：retention 的删除依赖级联，需逐个核对 migrations 000001-000009 的外键定义。
