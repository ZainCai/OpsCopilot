## 二、逐域发现

### 域 A · 并发/锁/内存护栏

三处锁外化（`d77f812` Gate.Admit、`c521b6e/ded386a` 判决落库 writer、ProcessAlerts 落库/AutoAttach）核查后**均未重蹈锁内 IO**：Gate.Admit 锁内只判决+快照复制、`Send` 全在锁外（`notify.go:244-271`，`TestGateAdmitSendsOutsideLock` 钉回归）；全局锁序 `n.mu→s.mu / n.mu→c.mu/d.mu→g.mu / n.mu→q.mu / g.mu→r.mu` 两两一致，无 AB-BA 环；`memguard` 淘汰全部发生在持有者锁内、`Guard.Over/Evicted` 不回调查询回调、gauge 在释放 registry 锁后求值，无递归锁死与并发 range 竞态；ingest 认领租约为单语句 `FOR UPDATE SKIP LOCKED … RETURNING` 原子认领 + `locked_by` CAS 回写（`ingest_queue.go:170-224`），多实例互斥成立。

- **[P1-A1→见域 B 汇总] 门禁监督器唤醒竞态**（详单在域 B P1-1，性质是并发问题）。
- **[P2-A1]** `leader.go:277-295` `heldConn` 在持 `l.mu` 期间执行 `pool.Acquire`（可阻塞至 max(retry,2s)）——`IsLeader()`（`/metrics` gauge，assembly.go:278）与 `Stop()` 在此期间被串行化；池耗尽+大 retry 间隔时 `Stop()` 先卡锁（10s 等待上限只覆盖之后的 runDone）。锁内 IO 的残留孤点。建议：Acquire 移锁外，锁内只做钉住/换出。
- **[P2-A2]** `noise_process.go:127/369-423` `persistedSig` 签名在 `n.mu` 内写、落库在锁外、失败回滚再拿锁——check-then-act 正确性依赖"ProcessAlerts 串行调用"这一**注释声明但未强制**的前提（`noise.go:49-50` 甚至称"不依赖宿主串行"）。当前唯一调用点为单采集 goroutine，不可触发。建议：把前提升格为断言或文档硬契约，或后半程入锁。
- **[P2-A3]** `noise_writequeue.go:186-202` + `main.go`/`Assembly.Close` 双保险调 `StopVerdictWriter`：首次超时后 writer 仍在挣扎，二次 `stop()` 再取 `len(q.ch)` 残量会**重复计入 sink_drops**（宁多不减的保守上界，注释自认；不丢通知）。
- **[P2-A4]** 租约 vs 慢批：默认 batch=20 × perItem≈15s ≈ 5min > lease=2min（config.go:498-503），慢批合法越租 → 他实例重领做**重复劳动**（结果幂等无害，`UpsertExternal` FOR UPDATE 恰一 isNew）。建议 lease≥批最坏时长或处理中续租。
- **[P2-A5]** 并发用例缺口：无"N 路并发 ProcessAlerts + 并发 StopVerdictWriter/SetVerdictSink(nil)"钉 RLock-vs-close(done) 不变式；memguard 无"淘汰进行中并发 gauge 求值"用例；leader `heldConn` 无并发用例。

### 域 B · 资源泄漏 / goroutine 生命周期

全枚举本轮新增 `go func`/ticker（选举环、gated 监督器、verdict writer、rca_auto worker、rca pipeline 临时协程、凭证清扫、Poller/Sweeper/Pruner/Host/Escalation/IngestWorker）：**除下述 1 项外全部挂 runCtx**、`select ctx.Done()` + `ticker.Stop()` 齐备；Close 链顺序正确（先停 writer 排水、`Leader.Stop` 等选举环归还 pinned conn、最后 `pool.Close`，pgxpool.Close 语义兜底，无向已关池提交的 panic 窗口）。**session 懒恢复无后台协程**（纯请求内同步，已核 internal/sessionstore 零 goroutine/ticker）；pinned conn 全仓唯一一处 `Acquire` 在 leader.go，try-lock 失败/降级/Stop 三路均 `Release`/`releasePinned`，无漏还；rca_auto pending 队列有界（64，满即丢+计数）。

- **[P1-1] `runLeaderGated` check-then-capture 唤醒竞态 → 降级后 leader-only 循环可长期不停（ADR-012 单 owner 违例窗口）**。`leader_gated.go:53-57`：`for gate.IsLeader() { … <-gate.Notify() … }` 是**两次独立加锁**，且顺序与 `leader.go:143-145` Notify 注释自订的标准姿势（"先取通道、select 等待、醒来重读 IsLeader"）**相反**。若 `setLeader(false)` 的 close 恰落在 `IsLeader()==true` 之后、`Notify()` 捕获通道之前（`leader.go:352-357` close-换新通道），监督器错过该次 demote、阻塞等新翻转，而 demote 后本实例通常不再翻转（锁被他实例持有）——Host 采集/降噪判决/Puller/Retention 已在非 leader 态继续运行，`cancel()/wg.Wait()` 永不触发。触发概率低（微秒窗口 × 翻转时刻），但后果正是选主机制要消灭的双写窗口。建议：进入等待前 `notify := gate.Notify()` 再判 `IsLeader()`（捕获-校验对调），或 LeaderElector 加一个锁内返回 `(leader, ch)` 的方法。非 leader 分支（:33-38）同型但后果是 fail-closed 晚开闸，无害。
- **[P2-B1]** verdict writer 生命周期只绑显式 `Stop()` 不挂 ctx（`noise_writequeue.go:205/285`）——server/Assembly 两条路径都调了 Stop，但绕过 `Assembly.Close` 的嵌入式用法会泄 writer。建议文件头注释补"Stop 是唯一退出点"。
- **[P2-B2]** `rca_auto.go:62/106` `seen` map 无淘汰（上界=进程生命周期 critical 事件数，量级小）。长值守卫建议对齐 memguard 做法。
