# 双链路事件来源方案（外部自动导入 ∥ 人工建单）· 供评审

> 基线：commit `8e2c465`（W9 事件域 DB 后端已落地）。本方案只讲设计，不含代码。
> 目标：回答"事件能否同时支持外部自动导入 + 人工界面建单，两条链路并行互不阻塞"。
> 结论先行：**可行，且建议采用**——现有事件域（状态机 + Store 接口 + 迁移 + 幂等）已经是天然的双链路底座，缺口集中在"来源标识、外部幂等键、异步导入通道、写路径鉴权"四件。

---

## 一、现状盘点（方案依托的既有事实）

| 已有能力 | 位置 | 对本方案的意义 |
|---|---|---|
| 事件实体 + 状态机 `open→acked→mitigated→resolved` | `internal/incident/incident.go` | 两条链路共用一套状态机，语义统一 |
| `Store` 接口（MemStore / PGStore 双实现） | `internal/incident/pg_store.go` | 写入收敛到单一出口，链路差异在入口层消化 |
| `incident` + `incident_cluster` 表（一簇一事件唯一索引） | `migrations/000004` | **天然的去重约束**：同簇不会建第二单 |
| 降噪簇 + 指纹去重 + 影子判决 | `internal/noise` | 外部自动导入的最佳上游：先聚簇再建单，天然抑噪 |
| 写路径鉴权（共享密钥 `X-OpsCopilot-Token` + 401） | `cmd/opscopilot/change_webhook.go` | 人工建单与外部推送的写端点可直接复用同一鉴权件 |
| 连接器抽象（Prometheus/Azure 只读、Host 调度、凭证闸门） | `internal/connector` | 外部事件源适配器可沿用同一装配与调度纪律 |

## 二、整体流程与数据流转

```
【链路 A：外部自动导入（异步、可积压、可重放）】
 监控系统/API/定时拉取
      │  EventSource 适配器（webhook / pull / 队列消费者）
      ▼
  ingest_queue（DB 表，接收即落盘，不丢）   ←── 幂等键：origin + source_ref
      │  worker 池（N=2~4，独立 goroutine，失败退避重试）
      ▼
 ① 幂等查重 → ② 关联判定（簇 / 指纹 / 相似候选） → ③ 建单 或 合并 或 忽略
      │
【链路 B：人工建单（同步、低延迟、人等结果）】
 控制台/API  ──写端点(鉴权)──► 直接建单 / 手动合并 / 手动关联簇

两条链路 → 同一个 incident.Store（同一张表、同一状态机）
读侧：REST /api/v1/incidents（只读） + 控制台
```

**互不阻塞的三条保证**（这是方案的核心，不是"两个入口写同一张表"那么简单）：
1. **物理通道分离**：外部走队列（异步写盘即返回 202），人工走同步 REST（直接返回单号）。外部源再慢、再突发，也不会占住人工建单的连接与事务。
2. **写入事务短**：单条写入 = 一次 upsert + 关联查询，全部带 5s 超时（PGStore 已落地）。worker 与 REST 各自持连接，互不排队。
3. **合并判定异步化**：疑似重复检测（相似计算）只在 worker 侧做，人工路径不等待——人工建单永远不会因为"正在算相似度"而卡住。

## 三、数据模型：区分与统一

**原则：单表统一 + 来源字段区分，不建两张表**（双表必然带来查询分裂与合并地狱）。

增量字段（迁移 000005）：

| 字段 | 类型/约束 | 说明 |
|---|---|---|
| `origin` | enum(`manual`,`webhook`,`prometheus`,`azure`,`pull`,`api`) | 来源通道，**区分两条链路的一等公民** |
| `source_ref` | text | 外部唯一键（如 alertmanager 的 `fingerprint`/事件 ID）；人工单为空 |
| `source_meta` | jsonb | 原始载荷留痕（审计与回放依据） |
| `dedup_key` | text | 归一化去重键（见第四节 L1） |
| `created_by` | text | 人（工号/账号）或系统标识（`system:webhook`） |
| `merged_into` | text | 被合并到哪一单（保留原单不删，可追溯） |
| `auto_close_policy` | enum(`auto`,`manual_only`) | 外部恢复能否自动关单（见风险 R2） |

**幂等唯一索引**：
```sql
CREATE UNIQUE INDEX idx_incident_external_idem
  ON incident (tenant_id, origin, source_ref) WHERE source_ref <> '';
```
- 外部链路：同一 `origin + source_ref` 重推 **只更新不新建**（天然抗重放）；
- 人工链路：`source_ref` 为空，走 `incident_id` 唯一约束，不受该索引影响。

**统一视图**：读侧不区分来源，只按 `state/severity/时间` 排序；需要区分时按 `origin` 过滤（`origin='manual'` 即人工单）——展示层自由，存储层不分裂。

## 四、重复与关联：三层递进（越往上越保守）

| 层级 | 判定依据 | 动作 | 是否自动 |
|---|---|---|---|
| **L0 幂等** | `origin + source_ref` 相同 | 更新既有单（追加原始载荷、刷新最近时间），不新建 | ✅ 自动 |
| **L1 簇/指纹关联** | 上游降噪已给出 `cluster_key`；或 `dedup_key`（节点 + 指纹 + 时间窗）命中 | 挂到既有事件的 `ClusterKeys`；若该簇已属另一单 → **不建新单**，记录关联并在原单追加证据 | ✅ 自动（`incident_cluster` 唯一索引兜底） |
| **L2 语义相似** | 标题相似度 + 节点重叠 + 时间邻近 | 仅标记 `dedup_candidates`（疑似重复待确认），由人一键合并 | ❌ 只提示，不自动合并 |

**关键判断：L2 绝不自动合并。** 运维领域把两个不同故障误并成一个是灾难级事故（影响面判断失真、处置职责混乱），宁可多一个"疑似重复"待确认列表。这是本方案最需要评审者认同的一条设计取舍。

**合并语义**：被合并单设 `merged_into` + `state=resolved`，保留原记录（审计可追溯），所有 `ClusterKeys` 转移到主单。

## 五、外部数据源接入的扩展方式

**抽象**：新增 `EventSource` 接口（与现有 connector 同构，位于 cmd 装配层，internal 边界纪律不变）：
```go
type EventSource interface {
    Name() string                      // 即 origin
    Start(ctx, emit func(RawEvent)) error  // 推模式：长驻监听；拉模式：内部定时
    Stop() error
}
```
**适配器类型**：
1. **Webhook 接收**（Alertmanager / 通用 HTTP）：复用现有写路径鉴权件，接收即入队；
2. **定时拉取**（工单系统、K8s Events、云厂商事件 API）：Host 调度（现有连接器已有 interval/cron 纪律），每次拉全量按 L0 幂等去重；
3. **队列消费**（Kafka/Redis Stream）：预留，M2 不实现。

**新增一个数据源的成本**：实现 `EventSource` + 在装配处注册一行 + 迁移里加一个 `origin` 枚举值。**不需要改事件核心**——这是选这个抽象的唯一理由。

## 六、风险点与应对

| # | 风险 | 影响 | 应对 |
|---|---|---|---|
| **R1** | **建单风暴**：大规模故障一次性灌入上千事件 | 库与人工看板被淹没 | ①外部链路一律先过降噪簇（一簇一单，天然抑噪）；②单源限流（时间窗内建单上限，超限聚合为"群体事件"摘要单）；③队列削峰 |
| **R2** | **外部恢复吞掉人工处置**：外部报"已恢复"自动关单，掩盖人正在处理的故障 | 处置中断、责任不清 | `auto_close_policy`：人工干预过的单（AckBy 非空 或 origin=manual）**默认不允许外部自动关闭**，只落"外部已恢复"标记待人确认 |
| **R3** | **误合并**（L2 自动化的诱惑） | 影响面误判 | L2 仅提示不自动；合并操作全审计（谁、何时、合并了哪两单） |
| **R4** | **乱序到达**：恢复事件先于告警事件 | 单被提前关闭或状态抖动 | 事件带外部时间戳；恢复先到则先建"预置单（open）"，后续告警按 L0 更新；状态机只前进不回退（现有设计已保证） |
| **R5** | **队列积压/重复消费** | 延迟或重复建单 | 队列带 `received_at` + 消费位点；消费幂等由 L0 保证（重复消费最坏结果是无变化） |
| **R6** | **写路径暴露**：人工建单是新增写端点 | 越权/伪造建单 | 复用现有 `X-OpsCopilot-Token` 鉴权件；人工端点额外要求操作者标识并落审计；只读 REST 网关不加写方法 |
| **R7** | **幂等键设计失误**（source_ref 取错字段，如用了随时间变化的 ID） | 重复建单失控 | 适配器必须声明 `source_ref` 语义并进单测（同一事件两次推送 → 仅 1 单）；上线前用故障注入器重放验证 |
| **R8** | **与影子降噪的边界**：M1 影子期不该真建单 | 影子期误动作 | 外部自动建单默认 `OPS_INCIDENT_AUTOCREATE=off`（影子期），转正后开启；人工建单不受影响（人主动行为） |

## 七、可行性与工作量

**可行性判断：高。** 每一项都落在已有能力上——状态机/Store/迁移/鉴权/连接器调度全部现成；新增部分是"字段扩展 + 一个队列 + 一个 worker + 一个写端点"，没有技术不确定性。

**分两期**：

| 期 | 范围 | 工作量 | 产出 |
|---|---|---|---|
| **一期（骨架可跑）** | 迁移 000005（来源字段 + 幂等索引）；人工建单写端点（鉴权复用）；Webhook 适配器 + 内存/DB 队列 + 单 worker；L0 幂等 + L1 簇关联合并 | ~3 人日 | 两条链路并行可用，外部重推不重复建单 |
| **二期（健壮与体验）** | 多适配器（pull / 云事件）；L2 疑似重复提示与人工合并；限流与群发聚合；审计日志；合并/建单全链路测试 | ~4 人日 | 抗风暴、可审计、可运营 |

**验收口径**（建议写进任务）：
1. 同一外部事件推送 10 次 → 仅 1 单；
2. 同簇 20 条告警 → 仅 1 单，20 条证据挂在单下；
3. 人工建单与外部导入同时进行 100 并发 → 人工路径 P95 < 300ms 且零失败（互不阻塞的硬指标）；
4. 人工接手的单收到外部恢复 → 不自动关闭，仅标记。

## 八、需要评审决策的三件事

1. **L2 是否接受"只提示不自动合并"**（我的强建议：接受）；
2. **外部自动建单的开关默认值**：影子期 off / 转正后 on（建议）；
3. **一期先做哪个外部适配器**：建议 Alertmanager Webhook（最常见、验证链路最短）。
