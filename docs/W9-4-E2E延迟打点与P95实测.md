# W9-4 E2E 延迟专项打点与 P95 实测

> M2 排期 W9-4。目的：补齐 **M1 出口标准 3**（告警链路端到端延迟 P95 < 30s）的
> 直接证据。M1 出口报告在标准 3 上标注的是"⚠️ 间接达标，无专项测量"，并明确
> 建议 M2 补一个 `verdict_written_at - alert_fired_at` 的字段级专项——本文件就是
> 该专项的实现说明与实测记录。

- 实测日期：2026-09-11
- 被测版本：`main` @ W9-4 提交（本提交）
- 实测环境：本机单实例（Windows / TimescaleDB 本地实例 / 无并发压测叠加）

---

## 1. 为什么需要这份专项

M1 期间对标准 3 的判断建立在两个**间接观察**上：

1. 判决表 `alert_event.occurred_at` 与故障注入器 30s 发射节拍逐条同秒对齐
   （416/416，无堆积、无滞后窗口）；
2. SSE 实时推送秒级可见。

这两个观察只能说明"没有明显积压"，**给不出延迟分布**，也无法把"源侧告警年龄"
与"opscopilot 自身处理耗时"分开。所以本次直接测量两个时刻的差：

| 指标 | 口径 | 说明 |
|---|---|---|
| `opscopilot_alert_fired_to_verdict_seconds` | `verdict_written_at − alert_fired_at` | **M1 报告点名的口径**，主证据 |
| `opscopilot_alert_fired_to_notify_seconds` | `notify_delivered_at − alert_fired_at` | 端到端（含通知）；enforce 模式 + 放行才有样本 |

- `alert_fired_at` = 上游告警的发射时刻：Alertmanager 形态取 `startsAt`，
  Prometheus `/api/v1/alerts` 形态取 `activeAt`。
- `verdict_written_at` **不是**内存判决时刻，而是**判决落库完成时刻**——落库是
  链路里最慢的一环（同步 PG IO），用内存时刻会系统性低估。
- `notify_delivered_at` = `Gate.Admit` 返回时刻，即该判决所有启用渠道的 `Send`
  都已返回。

## 2. 前置缺陷：Prometheus 源告警的发射时刻此前恒为空

**这是实现本专项时发现的真实缺陷，不修就没有可测的 `alert_fired_at`。**

- 现象：对接 Prometheus（而非 Alertmanager）时 `connector.Alert.StartsAt` 恒为
  零值，下游 `cmd/opscopilot/noise.go:toEvent` 只好兜底成 `time.Now()`。
- 根因：`internal/connector/prometheus` 只解析响应里的 `startsAt` 字段，而
  Prometheus 的 `/api/v1/alerts` 响应**只给 `activeAt`**（该接口形态没有
  `startsAt`/`endsAt`）。字段名对不上 → 恒空。
- 影响：把"告警年龄"抹成 0。表现为 (a) 延迟恒为 0、标准 3 不可测；
  (b) 无法区分"源侧积压"与"系统慢"；(c) 判决记录的 `occurred_at` 语义失真。
- 修复：`rawAlert` 增加 `ActiveAt`（`UnmarshalJSON` alias 同步），
  `normalizeAlert` 改为 **`startsAt` 优先、`activeAt` 回退**——Alertmanager
  形态下 `startsAt` 仍是权威值，不改变既有行为。
- 测试：`internal/connector/prometheus/prometheus_test.go` 新增
  `TestNormalizeAlertStartTimeShapes`（startsAt 形态 / activeAt 形态 /
  两者都有时 startsAt 优先 / 都没有则零值）。
- 验证：临时探针用连接器真实拉取注入器，确认 `activeAt` 已被解析为
  非零 `StartsAt`（探针已在提交前删除）。

顺手修掉注入器侧的一处测量噪声：`tools/faultinjector` 原本用 `time.RFC3339`
格式化 `activeAt`，**秒级截断**会给读数注入最多 1s 的均匀量化误差，把几十毫秒的
处理量级淹掉。改为 `RFC3339Nano`（下游 `parseTime` 用的 `time.RFC3339` 本身容忍
小数秒，兼容）。

暴露的指标：

```
opscopilot_alerts_processed_total                                  进入降噪引擎的告警数
opscopilot_noise_verdicts_total{reason="…"}                        按收敛原因分桶
opscopilot_alert_fired_to_verdict_seconds{_bucket,_sum,_count,_p50,_p95,_p99}
opscopilot_alert_fired_to_notify_seconds{…}
opscopilot_alert_latency_skipped_total{stage="verdict"|"notify"}   因源侧未给发射时刻而未观测的条数
opscopilot_noise_gate_{suppressed,dispatched}_total                Gate 累计计数
```

**`_p50/_p95/_p99` 是本项目的扩展**：Prometheus 官方直方图只能给桶内插值近似
分位，而验收要拿 P95 当证据——故额外保留 10000 个滑窗原始样本，按**最近秩法**
在真实观测值上精确计算（结果必为实测值，不插值）。无样本时渲染 `NaN`。

## 4. 实测环境与方法

- 服务：`opscopilot.exe`，`OPS_LISTEN_ADDR=127.0.0.1:8080`，
  `OPS_DB_DSN` → 本机 TimescaleDB，`OPS_NOISE_MODE=enforce`（闸门 + 通知全开），
  `OPS_NOISE_WINDOW=10m`（默认值）。
- 数据源：`tools/faultinjector`（Prometheus API 兼容的假数据源），
  `-scale 0.2 -warmup 10`（每场景 60s，剧本周期 360s），`OPS_PROM_URL` 指向它。
- 采集侧：prometheus 连接器默认 30s 采集节拍（`internal/connector` `defaultInterval`）。
- 剧本：A 单节点磁盘故障（n1 两条）→ C 静默 → B 交换机故障（n1/n2/n3 各一条）
  → C 静默 → D 无关噪声（n4/n5 各一条）→ C 静默，循环播放。
- 观测：每 30s 抓取一次 `/metrics`，持续约 14 分钟（覆盖 2 个以上完整剧本周期），
  共 39 次快照。
- 判定：`fired→verdict` 的 `_p95` 是否 < 30s。

> 说明 1：为制造**足量样本**，注入器场景时长按 0.2 缩放（顺序与相对时长不变）。
> 缩放只影响样本密度，不影响延迟口径。
> 说明 2：本实测中注入器把 `activeAt` 设为**响应请求的时刻**，故源侧年龄 ≈ 0，
> 读数即 opscopilot 自身处理段；源侧年龄的影响见 §7.1。

## 6. 对账与自证

1. **处理数恒等式**：38 = 5(new) + 26(dedup) + 7(merge)，且
   `processed − skipped = verdict_count` 在全部 39 次快照上成立，`skipped` 恒为 0
   → 延迟直方图的分母就是全部处理过的告警，**没有静默丢样本**。
2. **闸门恒等式**：`gate_dispatched + gate_suppressed = processed`（5 + 33 = 38），
   且 `notify_count == gate_dispatched` → 放行即通知，通知即打点。
3. **P95 是实测值**：`p95 = 0.5360255` 直接取自滑窗原始样本的最近秩统计，
   与同批 `p99 = 0.5378942` 同为真实观测值，非桶内插值。
4. 单测覆盖：`TestMetricsLatencyInstrumentation`（真库 + 假渠道，5 条告警 →
   断言计数/分位/`/metrics` 文本）、`TestMetricsSkipsAlertsWithoutStartsAt`
   （缺发射时刻 → 观测 0、`skipped` 1）、`TestAppMetricsNilSafe`。

## 7. 诚实边界（必须与结论一同阅读）

### 7.1 该差值含"源侧告警年龄"，不只是 opscopilot 的耗时

`alert_fired_at` 是告警在**源侧开始 firing** 的时刻；从那一刻到我们下一次采集
之间存在等待，其量级由采集节拍决定（默认 30s 轮询）。

本次实测中注入器把 `activeAt` 设为响应时刻，**源侧年龄 ≈ 0**，所以实测值
（P95 0.54s）可以读作"opscopilot 自身处理 + 落库 + 通知"的耗时。

真实拓扑下若按最保守估计：源侧年龄上界 = 采集间隔 = 30s；若告警发射相位相对
采集节拍近似均匀，则源侧年龄 ~ U(0, 30s)，其 P95 ≈ 28.5s。叠加处理段
P95 0.54s → **端到端 P95 ≈ 29.0s < 30s**。

这个估算的两个前提必须说清：
- 前提一：**采集间隔 ≤ 30s**（当前默认值）。若把间隔调大（如 60s），端到端 P95
  会突破 30s——标准 3 的达成与"采集间隔"是绑定的。
- 前提二：相位近似均匀。真实告警常成簇爆发，相位不一定均匀。
- 想拿到更大余量，两条路：缩短采集间隔（线性改善源侧项），或改用
  **push 形态**（Alertmanager 主动推，源侧年龄 ≈ 0，端到端 = 处理段 0.5s 量级）。
  本项目的链路 A 同时支持 push 与 pull（`cmd/opscopilot/pull_alerts.go`），
  push 拓扑下标准 3 的余量充足。

### 7.2 notify 侧样本天然少

`fired→notify` 只在 enforce 模式且判决**被放行**时才观测：一个故障域里只有首条
告警是 `new-incident`（放行），同域其余是 `cluster-merge`（不重复通知），重复
出现的是 `dedup-window`（不重复通知）。这是 W9-2 的**设计语义**（一个故障域一个
通知），不是丢样本。本次 5 个样本对应真实的 5 次送达，但样本量小，
**它的 P95 只宜作趋势参考，不宜当作统计显著的分布结论**；主证据是
`fired→verdict`（38 样本）。

### 7.3 `/metrics` 快照不是原子的

`alerts_processed_total` 在引擎锁内累加，而延迟观测发生在锁外 IO 完成之后。
抓取瞬间可能读到"处理了 N 条但只观测到 M 条"。为此增加了
`opscopilot_alert_latency_skipped_total` 来消除"源侧没给发射时刻"这一歧义；
其余差值即快照非原子，下一次抓取即一致。本次 39 次快照中未观察到该现象
（所有快照恒等式均成立）。

### 7.4 环境与规模

本机单实例、无并发压测叠加、DB 为本地 TimescaleDB、数据源为本地假注入器。
数值代表"正常处理路径多快"，**不代表峰值容量下的表现**（容量见 W9-6）。

## 8. 结论

1. **M1 出口标准 3 由"间接达标"升级为"直接达标（有字段级实测）"：**
   - `fired → verdict 落库` P95 = **0.536s**（38 样本），远低于 30s 红线；
   - `fired → 通知送达` P95 = **0.522s**（5 样本），同样远低于红线；
   - 处理段平均 0.380s / 0.326s。
2. **`/metrics` 是全链路的可核查出口**：处理数、判决原因分布、两段延迟分位、
   闸门拦截/放行计数都能在一条 HTTP 读路径上取到，且互相可对账
   （§6 的两条恒等式在全部快照上成立）。
3. **修掉了一个会让标准 3 不可测的前置缺陷**（Prometheus 告警发射时刻恒空，
   §2）——它同时影响判决记录的 `occurred_at` 语义。
4. **标准 3 的达成与采集间隔绑定**：当前默认 30s 采集 + 均匀相位假设下端到端
   P95 ≈ 29s（余量薄）；push 拓扑或缩短采集间隔可显著加厚余量。这条边界必须
   随结论一起交付。
