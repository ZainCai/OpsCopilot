# 第 1 章 P0 问题根因分析

## 1.1 问题描述

v1.2 C17 将数据库部署策略定为"首选云托管 PG/Timescale 服务（RDS PG 主备）"，但经核实（2026-08 官方许可文档）：云厂商 RDS/Azure PG **只提供 TimescaleDB Apache-2 版**，不含社区版（TSL）的连续聚合、保留策略、压缩特性——而数据层的"三级降采样（1m/5m/1h 连续聚合）"与"冷数据分层"**完全依赖这些特性**。部署决策与数据层设计直接冲突。

## 1.2 根本原因（三个层次）

| 层次 | 原因 |
|---|---|
| **直接原因** | C17 制定时未核对"托管 RDS 的 TimescaleDB 版本边界"这一事实，决策输入不完整 |
| **流程原因** | 高可用决策（二轮评审 C17）与数据层特性决策（一轮评审选型）发生在**不同评审轮次，无交叉核对机制**——v1.1 已提出建立 ADR（C13）但停留在待办，未实施，导致跨章节决策漂移 |
| **结构原因** | 数据层对 TimescaleDB 社区版特性的依赖是**隐式依赖**——没有一张显式的"关键外部依赖清单"（版本/许可/特性矩阵），任何后续决策都可能踩到它 |

## 1.3 暴露的架构薄弱环节

1. **决策耦合无守护**：架构中"选型 → 特性依赖 → 部署形态"是一条依赖链，但文档结构与评审流程都没有强制这条链上的任何变更触发下游复核；
2. **ADR 机制有名无实**：C13 识别了问题却排为 P2，本次事故证明它是 P0 级流程基础设施；
3. **交付物许可合规未前置**：单机私有化版将 TimescaleDB 打进 Docker Compose 分发——TSL 允许"作为 Value-Added Product 分发未修改二进制"，合规成立，但这一结论此前从未被显式记录和验证过（属于运气好，不是设计好）。

# 第 2 章 修复方案与实施

## 2.1 修复项 C19【P0·核心】：数据库部署策略修正

**调整内容**：
- **SaaS**：自建 TimescaleDB **社区版（TSL）** + Patroni + etcd 流复制主备（1 主 1 备 + 1 同步副本可选）。理由：① 本产品属 TSL 明确允许的 Value-Added Product，合规；② 自建才能保留连续聚合/保留策略/压缩三大成本特性；③ 降级路径不变（PG 原生分区）。
- **托管 RDS 降为 Apache-2 备选**：仅在"自建运维无人承接"时启用，启用即接受功能裁剪（连续聚合→定时物化任务、保留策略→cron 删除）。
- **Tiger Cloud 托管列为第三选项**：含社区版特性 + 零运维，供团队规模/成本变化时决策。
- **单机私有化版**：随 Docker Compose 分发未修改的 TimescaleDB 社区版二进制（TSL 允许），合规结论落档 ADR-006。

**影响范围**：
| 受影响项 | 影响 |
|---|---|
| §3.4 数据层 | 部署描述改写（见第 3 章） |
| §3.7 可用性 | RTO 从"托管自动故障转移 <5min"调整为"Patroni 自动故障转移 <5min（需演练保障）" |
| 运维成本 | 新增 Patroni/etcd 组件运维（SaaS 侧），单机版无变化 |
| 容量成本 | 主备两节点存储计算（与托管主备相当） |
| 备份策略 | pgBackRest 对自建 PG 完全兼容，无变化 |

## 2.2 修复项 C20【残余风险 R1】：Patroni 运维责任闭环

- **M1 指定数据库运维 owner**（角色而非人头，可由后端兼任），职责：Patroni 拓扑维护、故障切换演练、升级窗口；
- **故障切换演练与备份恢复演练合并为季度例行**（同一天执行，降低流程摩擦）；
- **决策阈值显式化**：团队 <3 人且无 PG 运维经验 → 触发"托管 RDS（Apache-2 裁剪）或 Tiger Cloud"的重新决策，阈值写入 ADR-006。

## 2.3 修复项 C21【残余风险 R2】：直通态降噪环形缓冲

- 直通模式下降噪缓冲改为**固定槽位环形结构（10k 告警槽位）**：满则丢最旧、保最新；
- 丢弃计数器实时累加，直通结束后在控制台输出"直通期间丢弃 N 条低优先级告警"报告；
- 效果：告警风暴下内存占用有硬上限，杜绝直通态 OOM 级联（直通模式的意义就是保命，不能自己先死）。

## 2.4 修复项 C22【残余风险 R3】：STS 落地可行性预研

- M1 期间对三朵云做中小客户可行性预研：AWS AssumeRole（跨账号信任配置）、阿里云 STS Token、Azure Managed Identity；
- **判定规则**：若任一朵云的配置复杂度超过"客户 15 分钟自助完成"标准 → MVP 降级为"长期只读 AK + 到期提醒 + 泄露快速吊销流程"，STS 顺延 M2 并写入选型差异说明；
- 到期提醒与快速吊销无论如何都在 M1 交付（P1-4 的最小集）。

# 第 3 章 修订后架构方案（受影响章节全文重写）

## 3.1 设计前提（不变）
多云中立不替换存量、只读优先、成本可控（待压测验证）。

## 3.2 数据层【v1.3 重写】

- **数据库**：TimescaleDB 社区版（TSL，自建）；SaaS 部署 = Patroni + etcd + 流复制主备（1主1备），RTO<5min（季度演练保障）；单机版 = 单库随 Compose 分发（未修改二进制，TSL 合规）；降级链：Tiger Cloud 托管 → RDS Apache-2（功能裁剪）→ PG 原生分区；
- **时态拓扑**：`valid_from/valid_to` + `(node_id, valid_from)` 索引，`as_of` 查询（同 v1.2 C15）；
- **Redis 双实例**：告警实例（AOF everysec、noeviction）/ 缓存实例（LRU）；会话状态落告警实例（P1-1 随 M1 第 0 周落位）；
- **审计独立存储**：append-only + 哈希链 + 每日外部锚点（同 v1.1 C3）；
- **冷数据分层**：>90 天指标降采样归档、>180 天审计明细转对象存储——**依赖的连续聚合与保留策略在自建 TSL 下完整可用**（本次修复的直接受益点）。

## 3.3 智能层【v1.3 修订点】

- 降噪直通模式：内存态规则 + **10k 环形缓冲 + 丢弃计数**（C21）；
- RCA：时点拓扑（as_of）→ 假设 → LLM 排序 → 证据链输出；直通补偿 RCA 复用管线（同 v1.2）；
- llm-gateway：双向过滤 + 三档降级 + 公平调度（同 v1.1/v1.2，无变更）。

## 3.4 可用性设计【v1.3 修订】

- 目标不变：控制面 99.9%、数据面告警链路 99.95%；
- 故障影响矩阵不变（v1.2 §2-C16）；
- 业务库高可用实现方式变更：托管自动故障转移 → **Patroni 自动故障转移**，RTO 承诺从"服务等级继承"变为"自建保障 + 季度演练证明"——运维责任显式化（C20）。

## 3.5 部署与运维【v1.3 修订】

- SaaS：K8s + **自建 Patroni 主备**；单机版：docker-compose（4 容器，DB 镜像内嵌）；
- 升级生命周期：golang-migrate 版本化 + 跨版本拒启 + 升级前自动备份（同 v1.2 C18）；
- **新增**：数据库组件纳入自监控（ Patroni 集群状态、复制延迟、切换事件告警到值班渠道）。

## 3.6 接口与数据流
与 v1.2 一致（as_of、direct_passthrough、compensatory 任务类型等均保留），本次修复不涉及接口变更。

## 3.7 安全设计
与 v1.2 一致；新增合规落档项：单机版分发 TSL 二进制的合规结论（ADR-006 附件）。

# 第 5 章 架构层反思：P0 暴露的设计缺陷与流程改进

## 5.1 暴露的缺陷

1. **隐式外部依赖**：对 TimescaleDB 社区版特性的依赖散落在各章节，无集中清单——这是本次 P0 的结构性根源；
2. **决策间无依赖守护**：跨轮次修订互不知情，单点正确的决策组合出错误的方案；
3. **合规结论未前置落档**：单机版分发许可合规此前是"碰巧成立"。

## 5.2 流程改进（立即实施，成本近乎零）

1. **建立「关键外部依赖清单」**（ADR-006 附件）：每个外部组件记录版本/许可/特性依赖/部署约束，任何部署/选型决策变更必须先过这张表；
2. **ADR 落地提速**：C13 从 P2 提升为立即执行——本次为 ADR-001~006 补齐（不用 Kafka、算子前置、LLM 单出口、Redis 双实例、审计分离、数据库部署策略），此后任何 P0 修订必须先写 ADR 再改文档；
3. **修订检查单制度化**：每次修订必须执行第 4 章格式的交叉检查并附在文档内（本报告即首例）。

# 第 7 章 容量模型三级估算（M2 W9-6 回写，2026-09-11）

> 兑现第 6 章步骤 7。全部数字的来源与可信度标注见
> `opscopilot/docs/容量模型-三级估算.md`；此处只留结论与决策相关项。
> 口径：单实例、单租户、采集节拍 30s。

## 7.1 实测基线（本机 30 天数据 + 压测/评估）

| 项 | 数值 | 来源 |
|---|---|---|
| `alert_event` 每行（含索引/chunk） | **414.6 B** | 实测（`hypertable_size`，7627 行） |
| 人工路径 P95（100 并发） | 建单 73.5ms / 流转 66.1ms / 列表 95.0ms，RPS≈1240 | 实测（口径③压测） |
| 告警链路 P95 | `fired→verdict` 0.477s / `fired→通知` 0.480s | 实测（W9 出口演练，三链路并跑） |
| 影子降噪准确率 | 100%（416 判决 34/34 段；W9 enforce 演练 9/9 段） | 实测（W6-3 / W9-1） |

## 7.2 三级估算（稳态活跃告警 = 主机数 × 2%，故障峰值 × 20%）

| 档 | 主机 | 判决行/天(峰值) | `alert_event` 增长/天 | 30 天稳态体积 | 判决写入/秒(峰值) |
|---|---|---|---|---|---|
| S | 100 | 5.8 万 | 24 MB | ~0.2 GB | 0.7 |
| M | 1,000 | 57.6 万 | 239 MB | ~2 GB | 6.7 |
| L | 10,000 | 576 万 | 2.4 GB | ~20 GB | 67 |

**连接数与被管主机数无关**（拉模式：单连接轮询聚合源），只随实例数与
浏览器会话数增长：PG 共享池 16 + 簇池 2（每实例）、Redis 2 实例、
SSE 订阅上限 200/实例。

## 7.3 结论与两个新增护栏项

1. **S/M 档（≤1000 台）无需架构变更**：延迟余量 1~2 个数量级，存储 30 天
   稳态 ≤2 GB，连接数恒定。
2. **L 档瓶颈不在吞吐，在两点**：
   - `alert_event` **写放大**：判决对每轮采集的每条活跃告警都落一行
     （放大系数 = 86400/采集间隔 = 2880 行/天/条）。触发点：日增判决 > 100 万行
     （≈350 条持续活跃告警）。缓解方向：判决只在状态/簇归属变化时落库
     （M3 候选，先观察）。
   - **进程内无上限 map**：噪声簇 resolve 后不淘汰、无 DB 形态下的审计内存态
     均无护栏。缓解：给 `Clusterer` 加与变更库同款的保留窗（范式已在
     W9-5 `change_prune.go` 验证，成本 < 0.5d）——**建议 M2 W10 顺手做**。
3. **可信度边界**：S 档结论可直接采信；M/L 档为线性外推，未在目标规模复测；
   压缩比（5×）与 `change_record` 行宽是推算（本机 0 行变更数据）。
   建议在 M2 出口评审前补一轮 30 分钟持续压测。
