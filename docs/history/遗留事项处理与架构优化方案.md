# 二、架构重审（收敛性）

## 2.1 新发现问题（本轮核实得出）：v1.2 C17 存在部署策略冲突

**事实链（依据官方许可文档，2026-08 核实）**：
1. TimescaleDB 分两个版本：**Apache-2 版**（只含 hypertable 基础分区能力）与**社区版（TSL）**（含连续聚合、保留策略、压缩、后台 job 等我们数据层规划依赖的核心特性）；
2. TSL 明确允许 **Value-Added Service/Product**——"在 TimescaleDB 之上提供增值服务"完全合规，仅禁止"把 TimescaleDB 本身当作 DBaaS 转售"。本产品（AI 运维副驾驶）属于前者，**许可层面无风险**；
3. **关键冲突**：v1.2 C17 写的是"首选云托管 PG/Timescale（RDS PG 主备）"。但云厂商（AWS RDS/Azure PG）只提供 **Apache-2 版**，不含连续聚合/保留策略/压缩——我们规划的"三级降采样（1m/5m/1h 连续聚合）"和"冷数据分层"**在托管 RDS 上不可用**。

**影响**：若按 C17 走托管 RDS，将被迫放弃连续聚合与保留策略，改用 PG 原生分区 + 自研 job 调度，降采样与冷分层成本显著上升，且与我们"一库两用、低成本"的选型初衷矛盾。

**修正方案（O1，最高优先级）**：
- 数据库部署策略**改为：自建 TimescaleDB 社区版（TSL）+ Patroni 流复制主备**。理由：① 我们是 Value-Added Product，TSL 完全合规；② 自建才能保留连续聚合/保留策略/压缩这些核心成本控制特性；③ 主备高可用用 Patroni 自建，运维成本在可接受范围（Patroni 是成熟标准件）；
- **RDS/Azure PG 降级为备选**，仅在"自建运维成本超出小团队承受"时启用，且启用即接受"Apache-2 功能裁剪 + PG 原生分区降级路径"；
- Tiger Cloud 托管（含社区版特性）作为第三选项列入，成本高但零运维，供后续规模决策。

## 2.2 已确认稳固的架构点（无需变更）

- 四层 + 横切分层、all-in-one 起步、三条硬约束（多云中立/只读优先/成本可控）；
- 时态拓扑（C15）、可用性矩阵（C16）、告警降级直通（C17 的直通部分）、单机版升级（C18）——四项 P0 本轮复核无误，且 C17 的"直通模式"不受部署策略修正影响；
- llm-gateway 单出口 + 双向过滤 + 三档降级；凭证信封加密 + 只读强制；审计独立 + 哈希链。

## 2.3 残余风险（需持续监控）

1. **自建 Patroni 的运维面**：从小团队"零 DBA"的现实看，自建主备仍是最大运维增量——需在 M1 明确"谁负责故障切换演练"，否则高可用设计停留在纸面；
2. **直通态内存降噪的容量上限**：告警风暴时内存态去重可能 OOM，v1.2 已标"压测标注"，本轮补充明确建议——直通态设固定环形缓冲上限，超限丢旧保新并输出降级提示，避免 OOM 级联；
3. **STS 依赖的合规前置**：P1-4 若引入 STS，需先确认目标云厂商的跨账号信任配置对中小客户的落地难度，避免"设计美好、客户配不了"。

# 三、架构优化方案（方向 + 预期效果）

| 优化项 | 方向 | 预期效果 |
|---|---|---|
| **O1**（P0 级修正） | 数据库部署改为自建 TSL 社区版 + Patroni 主备，RDS 降为 Apache-2 备选 | 保住连续聚合/保留策略/压缩三大成本特性；消除 C17 与数据层设计矛盾；高可用目标（99.95%）落地 |
| **O2**（排期调整） | P1-1 会话状态、P1-2 调用纪律守护提前至 M1 第 0 周 | 两条都是"越晚越贵"的债，提前成本近乎零；守护线先于业务代码，避免拆分返工 |
| **O3**（加固） | 直通态降噪加固定环形缓冲上限 + 降级提示 | 告警风暴时防 OOM 级联，直通模式可靠性提升 |
| **O4**（流程） | 全量待办补充 owner 与验收标准（见 §1.2 已列验收标准，owner 待团队分配） | backlog 从"清单"变"可跟踪任务"，防遗留项再次积压 |
| **O5**（依赖前置） | T2 Windows 冒烟与 T1 许可对照在 M1 第 0 周并行启动 | 两项结论分别牵动 P1-3 与部署策略，早定早解锁后续排期 |
