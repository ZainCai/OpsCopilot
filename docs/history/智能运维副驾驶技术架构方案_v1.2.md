# 第 2 章 P0 落实逐条核对

## C15 拓扑时态维度 ✅ 已落实

- **修改位置**：§3.4 数据层（时态模型设计）、§3.6 接口（GetTopology 签名与 REST 拓扑查询）
- **内容摘要**：
  - 拓扑节点/边表增加 `valid_from`、`valid_to`（NULL=当前有效），边变更时旧记录置 `valid_to`、插入新记录，事件化驱动；
  - `GetTopology(NodeRef, depth, as_of)` 新增 `as_of` 参数（默认当前时间）；REST `GET /topology?node=&depth=&as_of=` 同步支持；
  - rca-engine 诊断时强制以 `T0 ± 10min` 窗口查询时点拓扑，禁止使用当前拓扑分析历史事件；
  - 用户确认回流（v1.1 C1）记录同样带时间戳，置信度历史可追溯；
  - 存储成本论证：拓扑变更低频（中小租户 <50 边/天），时态增量存储年增量 < 1GB/租户，可忽略。
- **落实验证**：rca-engine 证据收集流程中拓扑查询调用点已明确携带 as_of；时态表加复合索引 `(node_id, valid_from)` 防查询退化。

## C16 可用性目标 + 故障影响矩阵 ✅ 已落实

- **修改位置**：§3.7（新增"可用性设计"节）
- **内容摘要**：
  - 可用性目标：**控制面（控制台/会话/配置）99.9%；数据面告警链路 99.95%**——告警链路等级高于交互功能；
  - 故障影响矩阵（依赖 × 功能失效行为）：

| 故障依赖 | 告警接收 | 降噪通知 | RCA | 会话 | 巡检 | 控制台 |
|---|---|---|---|---|---|---|
| TimescaleDB 宕 | ✅ 直通继续 | ✅ 直通继续 | ❌ 排队 | ❌ 降级直出 | ❌ 延迟 | ⚠️ 只读缓存模式 |
| 告警 Redis 宕 | ❌（入口重试） | ❌ | ❌ 排队 | ⚠️ 无会话态 | ❌ | ⚠️ 健康页 |
| LLM 供应商宕 | ✅ | ✅ | ⏸ 三档延迟队列 | ⚠️ 确定性直出 | ⏸ 延迟 | ✅ |
| 审计存储宕 | ✅ | ✅ | ✅（缓冲补写） | ✅ | ✅ | ✅ |
| 缓存 Redis 宕 | ✅ | ✅ | ⚠️ 变慢 | ⚠️ 变慢 | ✅ | ⚠️ 变慢 |
| 客户云 API 宕 | ❌ 该租户采集停 | ❌ | ⚠️ 仅存量证据 | ⚠️ | ⏸ | ✅（标注断连） |

  - 矩阵作为各组件冗余级别与告警降级设计的验收依据。

## C17 TimescaleDB 高可用 + 告警降级直通 ✅ 已落实

- **修改位置**：§3.7 可用性设计、§3.4 数据层部署形态、§3.6 数据流 A 修订
- **内容摘要**：
  - SaaS：首选**云托管 PostgreSQL/Timescale 服务**（RDS PG 主备，自动故障转移，RTO<5min），自建备选为 Patroni + 流复制主备；私有化单机版接受单库 + 每日备份（客户自担，文档明示）；
  - 新增**告警降级直通模式**：TimescaleDB 不可用时，collector → noise-reducer（切换内存态轻量规则，仅去重+时间窗聚合）→ IM 通知的告警链路继续工作，不执行 RCA 与落库；库恢复后：直通期间的告警批量回补落库并标记 `direct_passthrough=true`，触发一次补偿性 RCA（带原始 T0 的 as_of 查询，依赖 C15 时态模型）；
  - 审计库维持单实例（异步写 + 本地缓冲，宕机窗口仅丢缓冲，可接受）；
  - 缓存 Redis 保持单点（可重建，故障仅性能退化）。

## C18 单机版升级路径 ✅ 已落实

- **修改位置**：§3.9 部署与运维（新增"升级生命周期"节）
- **内容摘要**：
  - 数据库迁移用 golang-migrate 严格版本化；应用启动时校验 schema 版本连续性，**跨版本直接拒绝启动**并输出逐级升级路径（如 v1.2→v1.5 需经 v1.3/v1.4）；
  - 升级流程：`opscopilot upgrade` 命令内置三步——资源预检（磁盘/内存）→ **自动执行全量备份**（失败则中止升级）→ 迁移 + 启动新版本，失败回滚指引写入交付文档；
  - 版本兼容矩阵（应用版本 × 数据库版本 × 配置项变更）随每次发布更新到交付文档；
  - 安装脚本增加最小资源规格预检（初始值 4C8G，M1 实测修订）。

# 第 3 章 v1.2 更新后架构方案（关键章节）

## 3.1 设计前提（不变）
多云中立不替换存量、只读优先、成本可控（LLM 成本 < 订阅价 30%，待压测验证）。

## 3.2 分层结构（v1.2 标注版）

```
L4 应用层  Web 控制台 / IM 机器人 / OpenAPI（MCP 二期）
L3 智能层  降噪 │ RCA(时态拓扑 C15) │ LLM网关(双向过滤+三档降级) │ 巡检
L2 数据层  时态语义模型(C15) │ 指标/日志摘要/事件 │ 审计独立存储 │ 缓存
L1 接入层  云/开源监控/CI 连接器（worker 共享池/独占）
横切      租户权限 │ 凭证 │ 配置 │ 计量(待办) │ 备份容灾 │ 可用性设计(C16/C17)
部署      SaaS(托管 PG 主备 C17) / 单机私有化(含升级生命周期 C18)
```

## 3.3 模块划分（仅列变化项）
- **semantic-model**：时态化（C15），节点/边全量历史可回溯；
- **noise-reducer**：双模式运行——正常态（库读写）/ 直通态（内存规则，库恢复后回补）（C17）；
- **rca-engine**：拓扑查询强制 as_of（C15）；直通补偿 RCA 任务类型新增（C17）；
- **storage**：SaaS 托管主备（C17）；审计独立存储不变；
- 其余模块与 v1.1 一致（llm-gateway 双向过滤/三档降级/公平调度、patrol-scheduler、api-gateway、web-console 等）。

## 3.4 数据层（v1.2）
- 时态拓扑：`(node_id, valid_from)` 复合索引；变更事件驱动边失效/创建；
- 业务库：SaaS 托管主备自动故障转移；单机版单库 + 每日备份 + 升级前强制备份（C18）；
- 告警 Redis（AOF everysec、noeviction）/ 缓存 Redis（LRU）双实例不变；
- 冷数据生命周期策略不变（>90 天指标归档、>180 天审计明细转对象存储）。

## 3.5 智能层（v1.2 要点）
- RCA：证据收集（as_of 时点拓扑 + 指标/日志/变更）→ 假设生成 → LLM 排序 → 强制证据链输出；直通补偿 RCA 复用同一管线；
- 降噪：正常态四步流水线；直通态降级为"指纹去重 + 时间窗聚合"内存规则；
- LLM 网关：入向脱敏/注入检测 → 路由（主备）→ 出向 DLP → 计量；全不可用走 1h 延迟队列，超限明确失败。

## 3.6 接口变更汇总（v1.1 → v1.2）
- `GetTopology` / `GET /topology`：新增 `as_of`；
- RCA 触发接口：新增任务类型 `compensatory`（直通补偿）；
- 告警记录新增 `direct_passthrough` 标记；
- 其余接口（拓扑 confirm、RCA 结果 model_used/degraded_level 等）与 v1.1 一致。

## 3.7 可用性设计（新增）
- 目标：控制面 99.9%、数据面告警链路 99.95%；故障影响矩阵见 §2-C16；
- 冗余级别映射：业务库主备（C17）、告警 Redis 待 P1 评估主从、LLM 主备模型、其余组件无状态多副本；
- 降级直通：库宕告警链路不中断（C17）。

## 3.8 安全设计（v1.2 无新增变更，v1.1 设计全量继承）
凭证信封加密/只读强制/分层授权/审计哈希链/LLM 双向过滤/注入测试集，全部保留。直通模式期间不触发 LLM，无新增内容安全风险。

## 3.9 部署与运维（v1.2）
- SaaS：K8s + 托管 PG 主备；单机版：docker-compose（4 容器）；
- **升级生命周期（C18）**：版本化迁移 + 连续性校验 + 自动备份 + 兼容矩阵；
- 备份：RPO<5min/RTO<1h（SaaS）、季度演练；单机版一键备份 + 数据自管声明；
- 自监控：Prometheus/Grafana/Loki + 健康检查端点（带外监控列为 P2 待办）。

# 第 4 章 全面复审结论（v1.2）

## 4.1 分维度评估

| 维度 | 结论 | 要点 |
|---|---|---|
| **架构合理性** | ✅ 通过 | 时态模型补齐后诊断根基成立；"加速层/真相源""告警可达/诊断可用"两级分离原则一致；直通模式让降级从口号变成可验收行为 |
| **可扩展性** | ✅ 通过 | 时态设计不增加扩展负担（拓扑低频）；直通回补机制天然支持组件级弹性；插件化/Stream 抽象/worker 双模式三条扩展路径完整 |
| **技术选型适配性** | ✅ 通过 | 托管 PG 主备优于自建 Patroni（小团队运维面）；golang-migrate 是标准件；其余选型经两轮评审确认稳定 |
| **模块职责与依赖** | ⚠️ 基本通过 | C15/C17 修改点边界清晰、未造成新耦合；遗留：巡检/RCA 共享检查项仍直接调用（P1：抽 check-library）；llm 调度队列状态归属未定（P1） |
| **性能瓶颈** | ⚠️ 可控 | 时态查询已加复合索引；直通态内存降噪容量上限需压测标注；容量模型框架已建，M1 实测修订 |
| **安全风险** | ✅ 通过 | 直通期无 LLM 参与，安全面无扩大；审计缓冲窗口（秒级）已明示接受；凭证生命周期仍待 P1 补 STS/轮换 |
| **业务匹配度** | ✅ 通过 | 告警可达 99.95% 直接支撑"7×24 告警"卖点；时态拓扑支撑巡检周报与故障复盘场景（与产品方案场景对齐）；单机版升级设计匹配私有化客户"装了就忘"的真实使用模式 |

## 4.2 新引入问题自查（v1.2 合并是否引入新问题）

| 新问题 | 评估 | 处置 |
|---|---|---|
| 托管主备增加 SaaS 成本 | 单库 → 主备约 +60% 存储计算成本 | 可接受——告警链路 99.95% 目标的必然代价，成本计入容量模型 |
| 直通恢复后的重复告警 | 直通通知与回补落库可能重复触达 | 回补告警标记 `direct_passthrough` 且不重复 IM 推送，仅控制台可见 |
| 升级自动备份在无盘空间时失败 | 备份失败中止升级，客户可能卡死 | 预检提前报错 + 支持 `--skip-backup` 但需显式确认风险声明 |
| 时态表长期膨胀 | 拓扑低频，年增量 <1GB/租户 | 无需处理，纳入常规容量监控即可 |
