# 智能运维副驾驶（OpsCopilot）技术架构与整体技术方案

> 版本：v1.0 ｜ 日期：2026-09-08 ｜ 用途：方案评审与落地实施依据
> 前置文档：《AIOps 竞品分析与产品方案.md》（产品定位、目标用户、MVP 场景）

---

## 1. 设计前提与约束

产品定位决定技术形态，先固定三条硬约束：

1. **多云中立、不替换存量**：必须以"连接器插件"接入 AWS/Azure/阿里云/腾讯云 API 与 Prometheus/Zabbix/Grafana，客户现有监控体系原样保留；
2. **只读优先**：MVP 阶段所有采集与诊断均为只读操作，写操作（Runbook）二期上线且必须走审批闭环；
3. **成本可控**：面向中小团队，SaaS 单租户月成本（含 LLM token）必须控制在订阅价的 30% 以内，否则商业模式不成立——这决定了"算子前置、LLM 兜底"是架构级决策而非优化项。

部署形态：**SaaS 多租户为主 + 单机私有化版（Docker Compose）为辅**。单机版支撑数据不出门场景与外包服务商本地部署，与 SaaS 共用同一套镜像。

## 2. 总体架构设计

### 2.1 分层结构

```
┌─────────────────────────────────────────────────────────┐
│  L4 应用层    Web 控制台 / IM 机器人 / OpenAPI / MCP Server │
├─────────────────────────────────────────────────────────┤
│  L3 智能层    告警降噪引擎 │ RCA 引擎 │ LLM 网关 │ 巡检调度  │
├─────────────────────────────────────────────────────────┤
│  L2 数据层    语义模型(拓扑/变更) │ 指标/日志/事件存储 │ 缓存  │
├─────────────────────────────────────────────────────────┤
│  L1 接入层    云厂商连接器 │ 开源监控连接器 │ CI/CD 连接器    │
└─────────────────────────────────────────────────────────┘
   横切：租户与权限中心 │ 审计日志 │ 凭证管理 │ 配置中心 │ 计量计费
```

### 2.2 核心模块划分

| 模块 | 职责概要 | 部署单元 |
|---|---|---|
| **connector-runtime** | 连接器插件宿主，加载/调度/限流各数据源插件 | 每租户 1 个轻量 worker（SaaS）/ 1 个容器（私有化） |
| **collector** | 指标/日志/事件拉取与标准化 | 与 connector-runtime 同进程 |
| **semantic-model** | 资源发现、拓扑构建、变更关联（轻量 UModel） | 独立服务 |
| **storage** | 时序数据、日志摘要、事件、审计存储 | TimescaleDB + Redis |
| **noise-reducer** | 告警聚合、去重、抑制、风暴收敛 | 独立服务（计算密集，独立扩缩） |
| **rca-engine** | 根因分析：证据收集→假设生成→排序验证 | 独立服务 |
| **llm-gateway** | 多模型路由、prompt 管理、token 计量、降级 | 独立服务（唯一允许调用大模型的出口） |
| **patrol-scheduler** | 巡检任务调度（cron 语义）+ 报告生成 | 独立服务 |
| **runbook-engine**（二期） | 执行计划生成、审批流、执行、验证 | 独立服务 |
| **api-gateway** | REST/OpenAPI 入口、鉴权、限流、计量埋点 | 独立服务 |
| **mcp-server** | 对外暴露运维上下文的 MCP 接口 | 独立服务 |
| **web-console** | 前端控制台 | 静态资源 + BFF |

原则：**单租户内模块数量按规模伸缩**——小租户可合并为 2 个进程（all-in-one + worker），规模化后拆分。避免一上来微服务化把交付成本抬高（传统厂商的教训）。

## 3. 技术选型及理由

| 层面 | 选型 | 理由 |
|---|---|---|
| 后端主语言 | **Go 1.22+** | 连接器并发拉取（goroutine 天然契合多数据源轮询）；单二进制交付友好私有化；内存占用低 |
| 后端框架 | Gin + gRPC（内部） | 外部 REST 简单够用；内部服务间 gRPC 强类型契约，防止接口腐化 |
| 前端 | React 18 + TypeScript + Vite | 团队生态最熟；图表用 ECharts（拓扑图/时序图成熟） |
| 时序/主库 | **TimescaleDB（PostgreSQL 扩展）** | 一个库同时覆盖关系数据（拓扑/审计/计量）与时序数据（指标），中小规模下免维护两套存储；PostgreSQL 生态成熟、单机版可用纯 PostgreSQL 降级 |
| 日志存储 | 不自建日志平台——只存**日志摘要与模式聚类结果**，原始日志留在客户侧按需拉取 | 成本与合规双胜利，这是与重平台的关键取舍 |
| 缓存/队列 | **Redis（缓存 + Streams 轻量队列）** | 事件量级（中小租户 <1k 事件/分钟）用不着 Kafka；单机版组件数减一 |
| 插件机制 | **Go plugin 改用独立子进程 + gRPC**（HashiCorp go-plugin 模式） | Go 原生 plugin 有平台兼容坑；子进程隔离还带来崩溃隔离与多语言插件可能 |
| LLM 接入 | **llm-gateway 统一出口**，支持 OpenAI 兼容协议 + 国产模型（DeepSeek/Qwen）+ 本地 Ollama | 模型可插拔是硬需求（国内外合规、成本差异大）；统一出口才能计量 token、控制成本、做降级 |
| 告警/任务调度 | 内嵌 robfig/cron（巡检）+ Redis Streams（事件流） | 规模内不需要独立调度器 |
| 认证 | OIDC（对接企业 IdP）+ 本地账号（单机版） | 兼顾 SaaS 与私有化 |
| 部署 | Docker Compose（单机版）→ Helm Chart（SaaS/K8s） | 同一镜像两套编排，交付成本低 |
| 可观测自身 | Prometheus + Grafana + Loki（自监控，非产品功能） | 吃自己的狗粮，故障案例反哺产品 |

**明确不选的**：Kafka（量级不匹配）、K8s 强依赖（单机版要能跑在 Win/Linux 裸 Docker 上）、微服务全家桶（15 人以下研发团队养不起）、自训模型（用 API，不自研模型——竞品分析已证明模型层不是中小玩家的战场）。

## 4. 各模块职责与交互方式

### 4.1 connector-runtime + collector（接入层）
- **职责**：加载连接器插件；按租户配置的只读凭证轮询数据源；将异构数据（CloudWatch Metric、PromQL 结果、Zabbix event）标准化为内部统一事件/指标模型；限流与退避。
- **交互**：gRPC 调用 semantic-model 注册资源；将标准化数据写入 Redis Streams（事件）与 TimescaleDB（指标）；凭证只从 credential-store（横切）解密获取，**连接器插件本身接触不到明文凭证**（凭证由宿主进程代持，插件只拿到短时代理 token）。

### 4.2 semantic-model（数据层核心）
- **职责**：① 资源自动发现（云 API 拉实例/容器/负载均衡）；② 拓扑构建——两类来源：云厂商标签/安全组规则推断 + eBPF/Prometheus 服务调用关系（有探针时）；③ 变更关联——对接 Git/Jenkins/云变更事件，把"拓扑节点"与"最近变更"挂钩。
- **交互**：暴露 gRPC `GetTopology(node, depth)`、`GetRecentChanges(node, window)` 供 rca-engine 查询；资源变更事件写 Redis Streams 供下游订阅。

### 4.3 noise-reducer（告警降噪）
- **职责**：四步流水线——去重（指纹哈希）→ 聚类（时间窗 + 拓扑邻近 + 指标相关性）→ 抑制（已知维护窗口/低优先级规则）→ 收敛输出"告警簇 + 簇代表"。
- **交互**：消费 Redis Streams 中的告警事件；输出告警簇到 storage 并推送 api-gateway（触发 IM 通知）；把簇 ID 传给 rca-engine 触发诊断。

### 4.4 rca-engine（根因分析，产品灵魂）
- **职责**：对告警簇执行三阶段诊断：
  1. **证据收集**：并行拉取簇内节点的指标波动、日志模式突变、最近变更、依赖状态（全走已有连接器，只读）；
  2. **假设生成**：基于拓扑与规则库（变更→故障映射、资源瓶颈模式）生成候选根因，LLM 只在此步参与"证据综合与排序"；
  3. **结论输出**：强制结构 `{conclusion, evidence[], confidence, suggested_actions[]}`，每条 evidence 必须引用具体数据源与时间戳——**没有证据链的结论不允许输出**。
- **交互**：调用 llm-gateway（唯一 LLM 入口）；查询 semantic-model 与 storage；诊断结果落库并回调 api-gateway。

### 4.5 llm-gateway
- **职责**：prompt 模板版本管理；多模型路由（成本/延迟/合规三策略）；token 计量上报计费模块；超时降级（LLM 不可用时退回纯规则结论并明确标注"降级"）；幻觉防线（要求模型输出引用证据 ID，网关校验引用合法性）。
- **交互**：被 rca-engine / patrol-scheduler / 会话服务调用；全租户唯一 LLM 出口。

### 4.6 patrol-scheduler
- **职责**：巡检任务定义（cron/事件触发）、执行编排（调 rca-engine 的只读检查子集）、报告生成与历史 diff 对比、IM 推送。

### 4.7 api-gateway / mcp-server / web-console（应用层）
- **职责**：REST API（控制台与 OpenAPI）；MCP Server 把 `query_metrics / get_topology / explain_alert / run_inspection` 等能力以 MCP 工具形式暴露，企业自有 AI Agent 可直接接入（对齐 Datadog 的开放策略）；前端拓扑可视化 + 会话副驾驶 + 巡检报告页。

### 4.8 横切模块
- **credential-store**：云凭证加密存储（信封加密：KMS/主密钥 + 数据密钥），租户级隔离；
- **audit-log**：记录所有数据访问与 Agent 动作（谁、何时、查了什么、LLM 输出了什么）——对齐 STAROps 的全生命周期审计；
- **metering**：按"诊断次数 + token 用量"计量，支撑按效果计费。

## 5. 数据流与关键接口设计

### 5.1 三条核心数据流

**流 A：告警 → 降噪 → RCA（分钟级闭环）**
```
云监控/开源监控 → collector(标准化) → Redis Streams
  → noise-reducer(聚类收敛) → 告警簇
  → rca-engine(证据收集→假设→结论) → llm-gateway(LLM 排序)
  → 结论+证据链 → storage → IM 推送/控制台展示
```

**流 B：自然语言会话查询（秒级响应）**
```
用户提问 → api-gateway → 会话服务
  → 意图解析(LLM, 轻量模型) → 生成查询计划
  → connector 直查客户数据源(只读) / 查 semantic-model
  → 结果综合(LLM) → 带引用的回答
```

**流 C：定时巡检（小时级异步）**
```
patrol-scheduler(cron 触发) → 并行执行检查项(复用 rca 只读子集)
  → 生成报告 + 与昨日 diff → IM 推送 + 落库
```

### 5.2 关键接口（REST，节选）

| 接口 | 方法 | 说明 |
|---|---|---|
| `/v1/tenants/{tid}/alerts?state=clustered` | GET | 拉取告警簇列表 |
| `/v1/tenants/{tid}/alerts/{cluster_id}/rca` | POST | 触发根因分析（计费点） |
| `/v1/tenants/{tid}/rca/{rca_id}` | GET | 获取 RCA 结论+证据链 |
| `/v1/tenants/{tid}/topology?node=svc-a&depth=2` | GET | 拓扑查询 |
| `/v1/tenants/{tid}/inspections` | POST/GET | 创建/查询巡检任务 |
| `/v1/tenants/{tid}/connectors` | CRUD | 连接器配置（凭证走独立加密接口） |
| `/v1/tenants/{tid}/chat` | POST(SSE) | 会话副驾驶（流式返回） |

### 5.3 内部契约（gRPC，节选）

- `SemanticModel.GetTopology(NodeRef, depth) → TopologyGraph`
- `SemanticModel.GetRecentChanges(NodeRef, TimeWindow) → []ChangeRecord`
- `LlmGateway.Complete(TenantID, TemplateID, Vars, Budget) → Completion{tokens_used, citations[]}`
- `RcaEngine.Diagnose(ClusterID, Budget) → RcaResult{conclusion, evidence[], confidence}`

契约原则：**所有跨模块调用显式携带 TenantID 与预算（Budget）**——预算上限防止单次诊断 token 失控，这是计费正确性的前提。

## 6. 关键技术难点与解决思路

### 难点 1：告警降噪的准确率（砍错告警比不砍更糟）
- **思路**：三层递进——确定性的指纹去重（零误杀）→ 拓扑+时间窗聚类（保守，宁可多留簇）→ 相关性抑制（只在有明确规则或历史确认时启用）。降噪规则上线前先跑"影子模式"：只标注不执行，客户确认准确率 >90% 后才真正收敛告警。这是信任建立机制，也是竞品普遍缺失的。

### 难点 2：RCA 的幻觉控制
- **思路**：① LLM 只做"证据综合与排序"，不做原始数据解读（原始数据分析交给确定性算子）；② 输出强制引用证据 ID，llm-gateway 校验引用是否存在、时间是否匹配；③ 置信度低于阈值时输出"证据不足 + 需人工确认"，不硬给结论；④ 每季度用客户授权的历史故障回放验证准确率（对齐阿里开源 RCA 基准集的做法）。

### 难点 3：LLM 成本失控
- **思路**：算子前置过滤（只把压缩后的证据摘要喂给 LLM，单次 RCA 控制在 <50k token）；按次预算硬熔断；轻量模型做意图解析/摘要，强模型只在最终排序阶段使用；token 计量进 metering，月度成本报表对客户透明。

### 难点 4：多云凭证安全
- **思路**：只读凭证强制（产品侧校验 IAM 策略，写权限凭证拒绝录入）；信封加密存储；凭证不落插件进程；访问全程审计；凭证泄露告警（检测到异常调用模式时断连）。

### 难点 5：单机私有化与 SaaS 同构
- **思路**：所有模块无状态化 + 存储抽象层（TimescaleDB/纯 PG 可切换）；all-in-one 进程模式由 feature flag 控制；CI 对两种形态跑同一套集成测试。

## 7. 性能考量

| 指标 | 目标 | 手段 |
|---|---|---|
| 会话查询 P95 | < 5s | 意图解析用轻量模型；常用查询结果缓存（Redis，TTL 按指标频率） |
| RCA 端到端 | < 3min（含 LLM） | 证据收集全并行（goroutine 池）；算子先行，LLM 只处理摘要 |
| 告警降噪延迟 | P95 < 30s | 聚类窗口滑动计算；Redis Streams 消费者组水平扩展 |
| 单租户事件吞吐 | 1k events/min 起步 | 中小租户量级内 Redis Streams 足够；超限时按租户分片到独立流 |
| 巡检并发 | 每租户 50 任务 | cron 分桶 + 错峰调度 |
| 存储 | 单租户指标 90 天热数据 | TimescaleDB 连续聚合（1m/5m/1h 三级降采样）+ 原始数据转冷 |

压测基线：单 all-in-one 节点支撑 100 个中小租户（<10 实例监控规模），超出则按租户哈希分片 worker——SaaS 扩展模型简单直接。

## 8. 安全性考量

1. **凭证与数据**：信封加密；传输 TLS 1.3；原始日志不出客户环境（只取摘要/模式），天然降低数据出境与合规风险；
2. **授权模型**：借鉴 STAROps 的"人/Agent 分层"——用户账号权限与连接器只读权限分离；MVP 阶段产品本身无任何写能力，二期 Runbook 引入独立的 Agent 角色 + 每次写操作双人审批（发起人确认 + 目标系统 IAM 二次校验）；
3. **审计**：全量审计日志（数据访问、LLM 请求/响应、API 调用）保留 180 天，不可篡改存储（WORM 模式），支持导出对接客户 SIEM；
4. **多租户隔离**：应用层强制 TenantID 校验 + 存储行级隔离（tenant_id 索引 + RLS）；凭证与计量数据独立加密命名空间；
5. **LLM 合规**：模型可配置（国内租户默认国产模型），prompt 与数据不出 llm-gateway 白名单字段；客户可选"本地模型模式"（Ollama）实现数据零外发；
6. **供应链**：连接器插件签名校验；依赖锁版本 + 定期漏洞扫描。

---

## 9. 可扩展性考量

1. **连接器插件化**：新增数据源 = 写一个 go-plugin 子进程（gRPC 接口固定），不动核心代码；目标新连接器接入 <2 人周；
2. **模型可插拔**：llm-gateway 抽象 ModelProvider 接口，新模型（含开源本地模型）配置即接入；
3. **水平扩展路径**：stateless 服务直接加副本 → 事件流量大时 Redis Streams 按租户分片 → 极端规模引入 Kafka（接口已预留，替换 Stream 层即可）；
4. **功能演进**：Runbook 执行器、容量预测、SLO 自动化工单均为 L3/L4 增量模块，不动 L1/L2；
5. **生态开放**：MCP Server 让本产品成为客户 AI 工具链的一环而非孤岛——被集成能力本身是增长杠杆。

## 10. 里程碑与主要风险

| 阶段 | 范围 | 出口标准 |
|---|---|---|
| M1（0-2 月） | 接入层（Prometheus + 阿里云/AWS 连接器）+ 存储 + 告警簇展示 | 影子模式降噪准确率 >85% |
| M2（2-4 月） | RCA 引擎 + llm-gateway + 会话副驾驶 + 巡检报告 | RCA 证据链引用有效率 >90%，单次成本 <¥1 |
| M3（4-6 月） | IM 机器人 + 多租户 SaaS 化 + 计量计费 + 单机版 | 3-5 家种子客户试用 |
| 二期 | Runbook 审批执行器 + MCP Server + Zabbix/GCP 连接器 | 写操作零事故运行 30 天 |

**主要风险**：① 降噪/RCA 准确率不达预期 → 靠影子模式 + 历史回放提前暴露；② LLM 成本超预算 → 按次熔断 + 算子前置已是架构级保障；③ 单人维护面过大 → 模块边界清晰、优先 all-in-one 形态降低运维面。
